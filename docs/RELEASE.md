# Public release preparation

The publication source is the folder generated by `tools/prepareRelease.py`,
not the existing private working tree's Git history. Earlier commits contain
personal report paths and editor settings. This release process preserves those
local files and commits while creating a clean, reviewable public file set.

## Build and verify

From the root with the README environment active:

```bash
python -m unittest discover -s tests -v
node --test tests/labelTool.test.cjs
python tools/checkRelease.py
python tools/prepareRelease.py --out release/public
```

The build creates `release/public/`, `release/public.zip`, and a checksummed
`RELEASE_CONTENTS.json` inside the copy. It refuses to overwrite an existing
output. Use a new directory name for a later revision. Every included file is
listed explicitly in `tools/release-files.txt`; unlisted files are not copied.

Included: manual application, example manifest and downloader, original small
Ridge artifacts, exact frozen training snapshot, current development labels,
Statcast source CSV, selected research code/results, documentation, MIT license,
tests, and a GitHub Actions workflow.

Excluded: `.git`, `.idea`, virtual environments, downloaded videos, large model
weights, local video registrations, personal annotations and prediction reports,
internal handoff notes, and local logs. The build rejects common personal-path
and credential patterns in listed files. This check complements review of the
explicit file list; it is not a claim to detect every possible secret.

## Acceptance evidence

The first-run test starts an isolated server using a generated temporary MP4.
It exercises local-video registration, decoded frames, release checkpoints,
five-point prediction, saving, CSV export, and undo. Original project labels
and registered footage are never used for this test. Optional download and pose
packages are blocked in that server process.

`tools/checkRelease.py` checks the frozen model and label hashes, verifies the
model matches a refit on that snapshot, reproduces the pitcher-grouped score,
and checks resizing. It does not claim new external validation.

The GitHub workflow installs only the manual dependencies and runs these checks
on Python 3.12. Live MLB downloads are checked separately because availability
depends on the source and should not make every CI run depend on it.

## Publication boundary

Review the generated folder before publishing. It has no Git history. A public
repository can be initialized from that folder after owner approval. Do not push
the original repository's history as a substitute for the prepared file set.
This milestone prepares the release; it does not create a remote, push files,
or rewrite history. A new independent validation batch is deferred by the owner.
